# SQLite 接入阶段三设计（定案稿）：双写对账观察期 + 正式切换

状态：待用户拍板。基线：阶段二报告 PHASE2_REPORT.md（分支 sqlite-phase2）。
本稿对应阶段二报告 §8 的三项未定案：双写对账策略、Worker 硬失败姿态、
合流后迁移源形态对齐（第 5 节只盘点、不落码）。

## 结论摘要（推荐项）

| 议题 | 推荐 |
|---|---|
| 编辑保存的 IDB 镜像 | **差量镜像**（跟随 save_sync 的 upserted/deleted 集合走主线分条 delta 写）；全量镜像只保留在导入/迁移时刻 |
| 对账 | 每次冷启、列表首绘后异步逐篇哈希对账；**SQLite 为准**单向收敛 IDB；观察期退出判据 = ≥14 天且 ≥30 次冷启对账全等（或漂移均有已记录成因）、零硬失败回退、零未解释漂移 |
| 硬失败姿态 | 观察期：**自动降级 + 横幅告知，且降级为只读**（不沿用阶段二的可写直读回退）；正式切换并退役镜像后：**阻断提示 + 救援层导出抢救**。两个阶段姿态不同，理由见 §3 |
| 切换开关 | 运行时开关（localStorage `mynote_backend_v1`，救援面板可改）+ 构建默认值的两层形态；回滚不需重新部署 |
| IDB 副本保留 | 双写贯穿观察期 + 正式切换后再续 30 天；期满停写但不删除，删除另行决策 |

## 1. 双写口径

### 1.1 编辑保存：SQLite 主写 + IDB 差量镜像（推荐）

写路径顺序：persist 门面先调 Worker `save_sync`（SQLite 差量同步，阶段二已
落地，返回 upserted/deleted/unchanged 计数），提交成功后把同一组
upserted/deleted 的 id 集合交给 IDB 侧主线既有的 `save_backup_delta`
（分条 delta 写：单篇 put/delete + 信封/顺序有变才写）落镜像。

成本对比（阶段二与主线实测数）：

- **全量镜像**：302 篇库每保存一次重写约 4,985,700 B；全库处理一遍的实测
  量级是 zip 导入 258–364 ms、迁移约 0.45 s。编辑保存是防抖后高频触发的
  路径，每次保存都付全库代价，等于把 IDB 分条与 SQLite 差量两边已经拿到的
  写放大收益全部吐回去，不可取。
- **差量镜像**：写入量只跟本次改动篇数走。主线 idb-optimize 实测基线：40 篇
  库改一篇，落盘 20,570 B（全量写为 807,893 B，约 39 倍差）；302 篇库改
  一篇同理只是单篇字节 + 信封/顺序的小额增量。save_sync 的差量计数由
  storage 原生测试锁定，镜像侧复用同一集合，不另算一份差异。

镜像失败处置：SQLite 已提交即保存成功，**不因镜像失败让编辑保存报错**；
置 mirror-dirty 标记 + Diag warn 行，镜像一致性由 §2 的启动对账兜底修复。
Diag：在既有 `SQLITE save_sync upserted=N ...` 行尾追加镜像结果段
（`mirror=ok up=A del=B` / `mirror=fail <err>`），不新开一行，避免日志量翻倍。

### 1.2 导入 / 迁移时刻：维持全量镜像

导入与迁移本身就是全库操作（阶段二已落地：import_library + IDB 全量镜像、
迁移后 IDB 收敛写回），频率低、全量成本可接受，且每个这样的时刻都是一次
镜像「重新对齐基线」，能把差量镜像万一漏掉的漂移在此归零。维持不变。

### 1.3 其余数据面

- manifest/meta：Worker meta 与 IDB kv 镜像在变更时同写（量小，不做差量
  区分）。
- 附件：阶段二定案留 IDB 文件式、不入 SQLite，本来就只有一份，无双写问题，
  不动。
- quarantine_json（合流后新增的 kv 键）：不属于笔记库，不进 SQLite、不镜像，
  迁移与双写都必须原样保留不触碰（见 §5 第 3 点）。

## 2. 对账机制

### 2.1 触发与做法

- 触发时机：每次冷启、列表首绘完成之后异步执行一次（不阻塞列表呈现，
  与阶段二冷启 1.16–1.58 s 的既有预算互不干扰）；导入/迁移刚做完全量镜像
  的会话跳过（刚对齐过）。
- 做法：Worker `memo_hashes` 返回 SQLite 侧 id → FNV-1a 64 哈希表；主线程
  对 IDB 组装读出的逐篇字符串算同一哈希（复用阶段二对账口径，302 篇夹具
  聚合哈希 `8150782089912133320` 已验证两端口径一致）。逐 id 比对：
  哈希不同或单边缺失即漂移。
- 成本估算：主导成本是 IDB 组装读全库（约 5 MB 量级，与现行 IDB 直读加载
  同量级）+ 5 MB 的 FNV-1a 哈希（wasm 内为毫秒到数十毫秒级）。302 篇规模
  预计亚秒级完成；Diag 记实际耗时，超预算在观察期数据里会显形。

### 2.2 收敛方向与 Diag 行

- **SQLite 为准，单向收敛 IDB**：哈希不同 → 以 SQLite 侧篇内容覆盖 IDB
  镜像；仅 IDB 有的 id → 从镜像删除（SQLite 侧已删）；仅 SQLite 有的 id →
  补写镜像。对账过程对用户数据（SQLite 主库）只读、零写入。
- 例外：若本次会话发生过 §3 的硬失败降级，跳过收敛并记 warn——降级期的
  数据状态单独处置，不让对账把镜像侧的异常状态默默盖掉（本设计的降级是
  只读的，理论上镜像不会有新写入，此条为防御性闸门）。
- Diag 行设计：
  - `SQLITE reconcile ok memos=N ms=T`
  - `SQLITE reconcile drift put=A del=B ms=T`（收敛完成；A/B 非零即本次
    出现过漂移）
  - `SQLITE reconcile fail <err>`（warn；本会话镜像可信度存疑，下次冷启
    重试）

### 2.3 观察期与退出标准

观察期从 sqlite 构建首次上生产（用户真实数据跑双写）起算。退出（可切纯
SQLite，见 §4）须同时满足：

1. 日历时长 ≥ 14 天；
2. 冷启对账 ≥ 30 次，其中 `reconcile ok` 或 drift 能被已记录的
   mirror=fail 事件完全解释的次数占全部，**未解释漂移为零**（出现一次
   未解释漂移，计数清零重来）；
3. 期间零硬失败降级事件；
4. 真机门禁清单（DEVICE_GATE_CHECKLIST.md）在观察期开始前已跑通。

## 3. 硬失败姿态

场景：Worker 起不来或 SQLite 打开失败（初始化硬失败）。三选项：

| 选项 | 数据风险 | 用户感知 |
|---|---|---|
| A. 回退 IDB 直读保可用（阶段二现行） | 镜像若滞后，用户在旧副本上继续编辑产生分叉；SQLite 恢复后 §2 的「SQLite 为准」收敛会**静默丢弃**降级期编辑——真实数据损失且无提示 | 无感（最好），但出事时无声 |
| B. 阻断提示 | 零分叉风险 | 最差：Worker 偶发故障即锁死全部笔记，连看都不行 |
| C. 自动降级 + 横幅告知 | 取决于降级期是否可写：可写则同 A 的分叉问题只是有提示；**只读降级则零分叉** | 明确知道处于兼容模式，能看能搜能导出，不能改 |

**推荐：观察期采用 C 的只读变体**——自动降级到 IDB 镜像只读呈现 + 常驻
横幅（文案走五语言包，口径同多标签提示的玻璃覆盖层一族）+ Diag warn 行
`SQLITE backend unavailable, readonly fallback`。理由：观察期双写保证镜像
新鲜度到最后一次成功保存，只读降级不丢任何已保存数据；不可写就没有分叉，
SQLite 恢复后无需合并、对账照常。阶段二的 A 姿态只存在于从未碰过生产
数据的测试构建，可接受；一旦上真实数据，A 的静默丢弃风险不可接受，
**观察期不维持 A**。

**正式切换后姿态改为 B + 抢救**：切换并退役镜像写入后（§4），IDB 副本
逐渐变旧，只读降级会把旧数据当现行数据呈现，误导性比阻断更坏。故切换后
硬失败 = 阻断提示（说明原因 + 重试按钮）+ 救援层提供原文件导出（SQLite
库文件经 OPFS 导出、IDB 末次镜像导出），先保数据可抢救，再谈恢复。
两个阶段姿态不同是刻意的：姿态跟着镜像新鲜度走。

## 4. 切换与回滚

- 开关形态（两层）：构建层沿用阶段二的 sqlite-backend feature（决定默认
  后端）；运行时层新增 localStorage `mynote_backend_v1`
  （`auto`/`sqlite`/`idb`，persist 门面启动时读，`auto` = 跟构建默认）。
  救援面板加一项「以兼容模式启动」（置 `idb`），使回滚不需要重新部署——
  与救援层既有「只动开关、不动数据」的边界一致。
- 正式切换动作：观察期退出标准达成后，发一版构建默认 = sqlite 的生产
  构建（运行时开关默认 auto 即生效），Diag 记 `SQLITE backend default
  switched`。切换不搬数据（数据早已在 SQLite 里双写运行），是纯口径翻转。
- IDB 副本保留期：双写在切换后**再续 30 天**（镜像继续差量更新、对账
  继续跑）；30 天无回滚无异常，停镜像写入。此后 IDB 末次镜像原地保留、
  不主动删除；删除动作留给后续版本单独决策（与「绝不轻易清站点数据」
  的既有红线同向）。
- 回滚路径：窗口期内（镜像仍在写）回滚 = 救援面板置兼容模式或地址带
  `?backend=idb`，应用以 IDB 组装读启动、回到分条 IDB 口径继续读写；
  新鲜度保证：镜像差量跟随每一次成功保存，回滚最多丢「SQLite 已提交但
  镜像失败且尚未对账修复」的极小窗口，且这类事件在 Diag 里有 mirror=fail
  记录可查。窗口期外（镜像已停写）回滚会丢停写后的编辑，届时回滚须先走
  SQLite → IDB 一次性全量回灌（导入路径复用），不再是翻开关即达——此点
  写入切换后第 30 天的停写检查单。
- 非阻塞遗留：阶段二 §8 提的 Store::export_backup chrono 时钟面 wasm
  未验——本设计不引入 Worker 侧时间戳生成（时间戳仍在主线程产生），
  不阻塞阶段三；若后续要把导出搬进 Worker，先补验再动。

## 5. 迁移源对齐差异盘点（只盘点，开工时逐项改）

阶段二迁移演练的源形态是旧 IDB 全量形态（kv 单键 memos_json 整串）。
主线合流后 IDB 已变：v2 分条（memos 店逐篇 + kv 的 backup_meta /
memos_order / manifest_raw）+ 逐篇隔离落盘的 quarantine_json kv 键。
阶段三开工时要改的适配点共 6 项：

1. **迁移源读取入口**：迁移器入参从「kv 读 memos_json 整串」改为「按
   memos_order 组装读」（与主线 idb.rs 加载路径同口径）；还要兼容尚未升
   v2 的存量（打开即先走分条迁移，或迁移器双形态入参），二选一在开工时
   定。
2. **坏篇入参通道**：分条组装读会把单篇坏条目以字符串元素形态嵌进组装
   结果（令严格解析失败、不静默吞篇）；迁移器必须把组装结果先过
   core::migrate 的存量归一（含逐篇隔离）再入 SQLite，坏篇进隔离而非
   整库迁移失败——阶段二演练时隔离尚不存在，此通道是新增的。
3. **quarantine_json 键的保留**：迁移与镜像写回不得覆盖/删除该键；
   迁移完成戳与 meta 写入要避开它；演练断言需新增「迁移后 quarantine
   条目逐字在场」一项（救援层导出抢救路径依赖它）。
4. **迁移后收敛写回形态**：阶段二是整串写回 kv；新形态须走主线分条全量
   写（save_backup_full：信封 + 顺序 + 逐篇 put，单事务），复用主线实现，
   不在迁移器里另写一套。
5. **Diag 行与探针基线重对齐**：主线 IDB 保存打点已是
   `IDB save ok up=/del=/bytes=/full=` 口径（旧 `EDIT save_memos ok` 已
   退役）；阶段二演练探针与 §7 门禁里涉及 IDB 侧落盘形的断言（smoke 的
   readS3Doc 直读等）须改为组装读口径；probe_state_resilience（含 S7
   隔离、S9）须在合流后的 sqlite 构建上补跑全套（阶段二报告 §3 已标注
   欠账）。
6. **导入原子性衔接**：主线 save_all 已是横跨 kv+memos+attachments 的
   单事务；sqlite 下导入 = SQLite import_library 事务 + IDB save_all，
   两库无法同事务。设计上接受「两段提交」：导入 Diag 行须分别记两段
   成败，中途崩溃留下的半成品由下次冷启 §2 对账收敛（SQLite 为准）——
   开工时须补一个「导入中途杀页」演练场景验证此收敛。

## 6. 阶段三施工顺序（供拍板后排期）

1. §5 六项适配 + 迁移演练在合流后形态上重跑全绿（含新增两场景：隔离
   迁移、导入中途杀页）。
2. 双写（§1）+ 对账（§2）+ 硬失败只读降级（§3）落码，Diag 行齐备。
3. 真机门禁清单跑通（开工前置条件，先行）。
4. sqlite 构建上生产、观察期计时开始；退出标准达成后按 §4 切换。
