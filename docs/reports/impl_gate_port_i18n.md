verify_rustweb.sh 第 7 节的 i18n 深检（占位符齐平 + 僵尸键反向扫描）只在

## 二、移植落点与共源机制

- **共源文件 `scripts/i18n_deep_check.py`**：§7 的 python 实现整段抽出
  为独立文件，入参不变（`<WEB 目录> <仓库根>`）。verify_rustweb.sh §7
  改为一行调用（原 394 行 heredoc 删除，grep `def read_swift_string`
  全仓只在共源文件一处）；verify_ios.sh [9] 组在 T-4 后新增一段：
  调用同一文件、输出逐行透传（文案与 Web 侧同式）、按结论行登记
  7a/7b 两条 ok/bad，7c 警告只透传不判红；脚本异常（无结论行）按
  fail-closed 判红。
- **「动态认领注册表」的实测结论**：17 条认领**不是硬编码名单**，是
  解析引擎（D1 声明体 / D2 拼接后缀语料 / D3 调用点实参）运行时算出
  并逐条打 log 的。故单源化对象是引擎本身，不存在可抽的静态表；
  verify_ios.sh 内零副本、零硬编码认领表。
- **与任务预设的一处偏差（如实记录）**：任务预设现行树 §7 在补引用后
  应为绿。实测现行树（HEAD 6fe5ef0）跑原口径 §7 为 **46 条僵尸**：
  桥呈现批的 bridge.reason_*（D6 形态：`if let` 绑定自成员属性
  stateReasonKey）与 bridge.revoke_*（D5 形态：Lang.t(映射函数(...))）、
  权限中心批的 perm.* 40 键（D4 形态：键属性声明体
  `"perm.item_" + token` 拼接）——三批都新增了动态消费形态而未同步
  扩展 §7 解析，违反的正是 §7 注释自订的纪律（「新增动态形态时须
  同步扩展本节解析」）。本批按该纪律在共源引擎内补 D4/D5/D6 三个
  解析扩展（值域证据与守卫与 D1–D3 同口径：声明体字面量、同文件
  值域全集、恰为包内键才认领、逐条打 log），未另发明口径。
  pair_expired 本身已由补引用解决、不在 46 条内。
