# 标题胶囊真实短标题不居中（四修）——帧链端到端定案

- 日期：2026-11-28
- 批次：0.9.66 候选
- 实报：用户 0.9.65 真机纠正——不只是占位串，**实际标题字数少时也不居中**。0.9.65 已含二修（748b263 弹性帧）、不含三修（dc1d543 占位段落样式）。本批以用户实报为终判起点：二修对真实文本的设备效果从未被真量测验证过（其 T24-9 量测模型已被三修证明是自证式），视其为未证、端到端重查。

## 一、帧链逐环定案（当 meta 宽 > 标题内容宽时）

胶囊组合（MomentApp.swift `titleCapsule`）：`VStack(spacing: 3) { ZStack { TitleTextField + 截断覆盖层}, meta Text}`，外加 `.padding(.horizontal, 20)` 与 `.frame(width: capsuleWidth, height: capsuleHeight)`。

| 环 | 内容 | 结论 | 证据 |
|---|---|---|---|
| 0 | 胶囊帧：宽 = 定宽公式、屏幕居中 | 无误 | proven——0.9.63（真实标题）与 0.9.65（占位）两次截图像素量测：胶囊中心 ≈ 屏幕中心、宽与公式逐值合 |
| 1 | 胶囊 → 行：左右内距各 20 对称 → 行宽 = 胶囊宽 − 40、行中心 ≡ 胶囊中心 | 无误 | proven（源码构造） |
| 2 | 行内原生视图放置：meta Text 在 VStack 内居中 | 无误 | proven——两次截图 meta 墨迹中心偏差 −0.2pt（填满行宽不可分辨，但与行几何一致）；原生 SwiftUI 视图的容器居中行为正常 |
| 3 | **行 → 字段帧：representable 平台视图（UITextField）的有效帧宽与行内落点** | **坏环** | proven（设备）+ proven（源码依赖形态）——见下 |
| 4 | 字段帧 → 字形：`textAlignment =.center`（makeUIView 钉死） | 构造在位、效力依附环 3 | proven（源码）；帧宽 = 内容宽时居中无从发挥（等宽帧内左排与居中同形） |
| 5 | 占位呈现：段落样式.center（dc1d543） | 构造在位、效力依附环 3 | proven（源码）；合成复核见 §三 |

**环 3 定案**：
- 0.9.63 设备实况（ 二修提交自带截图像素量测）：真实短标题「使用指南」× 宽 meta，字形墨迹左缘与行左缘逐值重合、中心偏差 15.3pt = (行宽 − 标题宽)/2。即字段有效帧 = **内容宽、坐行左缘**——既不是行宽，也没有被任何容器居中（若容器居中了内容宽帧，墨迹中心应合行中心、偏差归 0；实测偏差恰为全额半差，唯一解是帧坐左缘）。
- 二修的补救是给字段加 `.frame(maxWidth:.infinity)`，其机制主张「帧布局占满行宽并居中其内容」属**意图级断言**：弹性帧向子视图透传父级提议，representable 的 `sizeThatFits` 在决定性量测一读落在哪一档（definite 回告提议宽 / unspecified 回告内容宽）不由该修饰符钉死；而平台视图帧随 `sizeThatFits` 回告值走——这一点恰由 0.9.63 实况反证（无显式帧时平台帧 = 内容宽回告值）。二修后无任何设备量测复核过环 3（T24-10 只锁修饰符在位、T24-9 是自证模型）。
- 0.9.65 用户复报真实短标题仍不居中 ⇒ **二修补救在设备上证伪**（用户实证即终判）。SwiftUI 内部量测遍次的精确病理（哪一遍的提议形态决定了最终帧）从代码不可判、标 **unknown**——本批的修法与验收都不依赖它：修法使帧宽不再经协商产生（§四），验收由设备探针直接量帧（§六）。

## 二、二修结论的证实 / 证伪分账

- **证实**：二修对 0.9.63 设备状态的诊断（字段有效帧为内容宽且坐行左缘、偏差 = (行宽 − 标题宽)/2、独「短标题 × 宽 meta」格暴露）——像素量测在案，本批帧链复核与之全合。
- **证伪**：二修的补救机制（弹性帧使「字形块中心恒合行中心」）——0.9.65 真机复报即否证。其断言体系同罪：T24-10 锁的是修饰符字面在位（构造 ≠ 实效）、T24-9 的 `centerDeviation` 把居中原点写死进算式（originX 按居中排布构造、偏差恒 0），两者都测不到环 3 的真实构型。
- 教训（与三修同型、三度重演）：凡「居中」类主张，量测原点必须来自被测排布之外的数据；锁修饰符在位不等于锁机制成立。本批断言按此重做（§五）。

## 三、dc1d543（三修·占位段落样式）合成复核

- 三修给占位串钉段落样式.center 是**必要环**：占位绘制对齐只认属性串自带段落样式，字段 textAlignment 不及——此定性源码可证、不推翻。
- 但它**不充分**：占位串在字段帧内按段落样式排布，帧若仍是环 3 的坏构型（内容宽帧坐行左缘；空文本时内容宽 = 占位串进距宽），段落居中在等宽帧内是空转——视觉上与未修无别。三修报告当时以 T24-11 结构锁 + 模型格收口，未复核帧链合成，是其留账的真实缺口。
- 本批环 3 根治后合成成立：字段帧 = 行宽（定值）→ 文本本体经 textAlignment.center、占位经段落样式.center、覆盖层经 multiline.center，三呈现者在同一全行宽帧内各自居中。占位格的端到端设备验收在本批格口内（§六场景 placeholderEdit 格：字段帧偏差 + 插入点偏差实测；占位墨迹本身无文本输入面可量，经帧 + 段落样式合成判读，证据上限如实标 inferred-by-composition）。

## 四、根治（布局单点）

**MomentApp.swift `titleCapsule` 字段修饰链**：`.frame(maxWidth:.infinity)` → **`.frame(width: capsuleWidth - 40)`**。

- 帧宽由胶囊自身的定宽值派生：capsuleWidth 是本视图已算出的定值（定宽公式 + 钳限），减左右内距 40 即行宽——与 `activateTitleFromCapsule` 落点映射的 `rowW = capsuleWidth - 40` 同源同式（T24-12 跨点一致性锁）。
- 为何这回不经协商：定宽帧（_FrameLayout）对子视图恒以定值提议（每一量测遍次同值），representable 的 sizeThatFits 决定性一读必走 definite 分支回告行宽，平台帧随之 = 行宽。弹性帧与尺寸契约两度失败的共同点——帧宽的产生依赖协商结果——被整体移除。
- 保全项逐字未动：胶囊定宽公式/钳限、弹性增长动画（`.animation(value: capsuleWidth)`，帧宽随 capsuleWidth 同步动画）、内距、ZStack 结构、覆盖层（其手势坐标系以行左缘为原点、帧宽恒行宽——定宽帧下 ZStack 宽 = 行宽，与此前同值）、落点映射（[26] 算式与 rowW 来源不变）、meta 行、紧凑态（capsuleWidth 已含 chrome 扣减、内距同为 20，行宽公式同构）。
- 无特判、无补距：短/长、空/实、展示/编辑全格同一构造。

## 五、断言（防自证重演，逐条说明为何不是自证）

1. **T24-9 改判（废除自证量测）**：旧 `centerDeviation` 已从 TitleCapsuleLayout 删除——它把块原点按居中排布写死（`originX = hPad + (rowW − blockW)/2`），偏差恒 0、测的是前提不是呈现。新模型 `inkCenterDeviation(capsuleWidth:fieldFrameX:fieldFrameWidth:)` 以**字段帧构型为外部入参**：字形块中心 = 帧中心（居中语义的 UIKit 定义），偏差 = |帧中心 − 胶囊中心|。表驱动双向受验——定宽帧构型（原点 = 内距、帧宽 = 行宽）偏差归 0；坏构型（原点 = 内距、帧宽 = 内容进距宽）必须复现两次**设备实测**偏差（0.9.63 格 15.3、0.9.65 格 14.7；模型按进距宽算得 14.0/13.5，与墨迹量测差 1.3/1.2 = 墨迹宽 < 进距宽的口径差，容差 1.6 并注明来源）。**为何不是自证**：期望值来自设备截图像素量测（独立于被测代码的数据），且同一模型能同时产出 0 与非 0——若模型被写成恒 0，坏构型对照恰红。定宽公式案例的期望宽仍按 Web 公式手算（独立于被测算式，此部分初版即非自证、保留）。本表职权边界明示：它验「构型 → 偏差」的模型与公式，**不验 app 实际建成哪种构型**——那由 2/3 两条守。
2. **T24-10 改判（构造锁换代）**：字段修饰链内必须有 `.frame(width: capsuleWidth - 40)` 且不得再有 `.frame(maxWidth:.infinity)`（防弹性帧叠加回潮）。**定位如实**：这是构造锁——锁帧宽的来源是胶囊定宽值这一构造事实，不冒充实效量测（弹性帧时代正是把构造锁当实效用才出的事）；实效由第 3 条的设备探针终判。
3. **T24-12 新增（跨点同源 + 探针链锁）**：① `capsuleWidth - 40` 字面在 MomentApp.swift 恰两处（定宽帧 + 落点映射 rowW）且映射段内在位——两处独立代码同出一式，任一处改道即红；这是跨点一致性检查，非同一算式自证。② 探针全链在位（控制面弱引用/读数法、注册面状态键、探针与场景登记）——守「装机后能以数字验收」的通道本身。
4. **负对照（本机实做）**：/tmp 副本中把定宽帧改回弹性帧 → T24-10、T24-12 恰红，T24-9 仍绿——与分工互证（模型层测不到构型、构造锁不可省，与三修负对照同型结论）。

## 六、设备侧量测钩子（本批关键交付）

- **读源**（TitleTextField.swift）：`TitleFieldControl` 新增字段视图弱引用（representable 在 make/update 登记）与 `titleGeometryString()`——一次读成串（窗口坐标）：字段帧 f、字形块两缘 g（非空文本时经 `caretRect(for:)` 取首/尾插入位 x，即字形块左右缘的布局真值）、空文本插入点 c、文本绘制矩形 t。胶囊注册面（editor.titleCapsule）新增 `titleGeometry` 状态键原样回报。
- **探针**（MomentBridgeUITest.swift `UITestProbes` 第七件 `title_geometry`，经 uitest_measure 调用）：组合胶囊帧（注册面 frameInWindow）与状态键，出数——capsuleCenterX / rowW / fieldW / **fieldCenterDev** / **glyphCenterDev** / caretDev / textRectCenterDev（皆对胶囊中心的偏差，窗口坐标），带 truncated/focused 标注与两读落定标（settled）。截断态呈现者是覆盖层、字段字形读数不代表呈现，payload 以 truncated 标注、字形偏差仅 truncated=false 时有判读义。
- **场景** `title_center_geometry`（目录已登记，夹具.title，矩阵 EDT-62）：四格——短标题（「自检短」3 标量，宽 ≈41 < meta ≈68）展示态、短标题编辑态、长标题截断对照（只判字段帧）、空占位格（编辑态清草稿不提交——提交会落「无标题」回退串使呈现者消失；escape 还原收口）。短标题格带**判别力守卫**：rowW − glyphW ≥ 10（两量皆设备实读），格不具判别力时响亮失败、绝不空过。每格断言 fieldCenterDev ≤ 0.5、字形格 glyphCenterDev ≤ 1.0、占位格 caretDev ≤ 1.0，原始 payload 入 step 记录。
- **证据上限（如实）**：探针读的是设备真实布局值（帧与 caretRect 皆 UIKit 布局真值、非模型推导），但本批无法装机自验——探针与场景均为**待 0.9.66 装机后主线首跑**状态；字形像素栅格不在证据面（caretRect 是布局值不是像素），占位墨迹居中经帧偏差 + 插入点 + 段落样式合成判读。
