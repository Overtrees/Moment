## R-1 标签 chip 定高裁字 —— 落码（类 B）

三体 chip 全改最小高承载（MomentApp.swift）：

| 位点 | 字体 | 旧 | 新 |
|---|---|---|---|
| 行卡 chip（titleRow 标签区） | f10（caption2 同源） | `frame(height: 18)` | `frame(minHeight: 18)` |
| 方卡 chip · 图文（squareTags small） | f10 | `frame(height: small ? 18 : 20)` 之一 | `frame(minHeight: small ? 18 : 20)` |

口径：Web 的 18/20 是 **line-height 本体**（base.css:354-358 行卡 font 10/line-height 18、474-495/546-556 方卡 11/20 与 10/18）——默认档文字实际行高（f10 ≈13、f11 ≈14.3）小于帧值，minHeight 托底使 chip 高恒为 18/20、**逐值不变**；AX5 文字行高 ≈42（f10）/≈47（f11）时随字生长，不再被 glassControl 纵向裁字。行卡 chip 所在行盒高 20×titleFontScale 同步缩放（AX5 ≈62 > 42），恒容得下、不联动改账。两处 chip 注释已同步记明此口径，防按 Web 行高值「恢复」定高。

连带改判：F30-8 原锚 `.frame(height: small ? 18 : 20)` 计数 2 随落码改 minHeight 形，注释与 ok 文案已留痕（改判理由同上，机制锁转 DT36-8）——沿各组「改锚须过目」原口径执行。

## R-5 首页列表模式 iPad 无宽上限 —— 销项（不设上限，判据在册）

不落码，判据三条（均有出处）：

1. **可达域同构**：列表模式的出现条件是 `homeWide == false`，其谓词 `width ≥ 768 || (横向 && height ≤ 560)` 与 Web 宽屏 media query（base.css:371 `@media (min-width: 768px), (orientation: landscape) and (max-height: 560px)`）逐字同构。iPad 全屏两向宽度恒 ≥768 → 恒走网格（1240 上限 + 页眉同轴已在，L-1/F30-15）；列表只在 iPad 分屏/侧拉等 <768 窗口出现，此时全宽行即正确贴合（与 iPhone 同形态）。
2. **Web 同域无上限**：该 media query 之外，Web 窄形态 `.container` 无 max-width（全文件 max-width 仅见宽屏段的 1240px 与元素级口径），列表行全宽拉伸——原生同口径、行为等价；单独给原生列表加居中上限反而偏离 Web。
3. **页眉同轴账相容**：<1280 时页眉横内距恒 20、列表行 insets 16，同域同账；加宽上限会与此账脱钩。

结论：R-5 不是缺口，是形态谓词的自然结果，销项登记。
