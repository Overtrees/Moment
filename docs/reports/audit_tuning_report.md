# 调优评估报告：在 1:1 基线之上，Rust 重构可做的交互/功能/渲染调优

- 性质：只读评估，未改任何代码。结论均为明确表态，供主线排期与用户裁决。
- 前提（不可动）：文档格式冻结（block JSON + ZIP 字节兼容）；已实测对齐的度量与行为不因调优回退；调优只动「交互如何发生」，不动「数据长什么样」。
- 判定框架：每项先分清是「原版缺陷」（原版自己也没想清楚/实现受限）还是「原版设计意图」（看似怪但有意为之）。前者可调优，后者默认保留。

## 一、头号议题：标题/引用/标注/待办回车不拆文本、块后插空段

### 1.1 现状

原版 `src/app/editor.js:2076-2114`：焦点在任何非段落块（标题/引用/标注/待办/卡片等，图文卡文字区除外）按 Enter，一律 `preventDefault`，在该块**后**插入一个空 `<p>`，光标移入空段，原块文本整段保留——不论光标在块首、块中还是块尾，不论原块是否为空。Rust 已按此 1:1 落地（`rust/apps/web/src/editor.rs` 的 `op_split` styled 分支，注释引 B1）。

这条规则的本质：原版用**一个统一分支**处理所有样式块，实现简单、心智模型单一（「Enter = 到下一段正文」）。它是有意为之的简化，但简化在不同块类型上的代价差得很远——这是本次评估的核心。

### 1.2 主流编辑器对照

| 场景 | Notion | Apple Notes | Obsidian | 飞书文档 | Word / Google Docs | Mynote 原版 |
|---|---|---|---|---|---|---|
| 标题·光标在末尾 Enter | 下方新建正文段 ✓与原版同 | 下一行切正文样式 ✓同 | 新行即普通行（md 无样式延续）✓近同 | 下方新建正文段 ✓同 | 拆出空标题段（靠「后续段落样式」回正文） | 插空段、光标过去 |
| 标题·光标在中间 Enter | **拆成两个同级标题** | **拆开，两段同为标题样式** | 只是文本换行（无块概念） | **拆成两个同级标题** | **拆开，两段同样式** | 不拆，光标跳到块下空段 |
| 待办·Enter（有内容） | **新建下一条待办** | **新建下一条清单项** | **新建下一条任务项** | **新建下一条任务** | 列表延续新建项 | 插空段（不是待办） |
| 待办·空待办 Enter | 退出为正文段 | 退出为普通行 | 退出列表 | 退出为正文段 | 退出列表 | 插空段，**空待办留在原地** |
| 引用·Enter | 引用内续行；空行 Enter 退出 | —（无引用块） | `>` 行延续，空 `>` 行退出 | 引用内续行；空行退出 | 拆开同为引用样式 | 插空段，引用不延续 |
| 标注（callout）·Enter | 在标注容器**内部**新建正文块 | — | —（插件语义不一） | 标注内续写 | — | 插空段（且 Rust/原版里标注本是 md 源段落，见 1.4） |

两条硬结论：

1. **标题末尾、引用外正文衔接这些高频路径，原版与主流一致**（Notion 的标题末尾行为与原版逐字相同）。原版规则在 80% 的使用路径上并不「怪」。
2. **待办是全场唯一的硬伤**。「逐条列任务、每条按一次回车」是清单类块的定义性交互，五家主流无一例外做列表延续。原版路径下，写完一条待办按回车得到一个普通段落，想写下一条必须再走斜杠命令（打 `/` → 输过滤词 → 选中待办命令），**每条多出至少 3 次交互**；连写 10 条就是约 30 次多余操作。空待办回车更糟：主流是「退出清单」，原版是留下一个空待办在原地、下方多一个空段，残留垃圾块。

标题中间拆分是第二分歧点：主流一致拆开，原版不拆、光标瞬移到块下方。笔记应用的标题通常短，中途回车多为误触或改行宽，发生率低；且不拆有一个真实优点——标题永不被意外劈成两截。但「光标瞬移」本身（见 1.3）是体验毛刺。

### 1.3 衔接与过渡（与拆不拆无关，两版共同的问题）

- **高度跳变**：插空段后下方内容瞬时下移一行高。原版在单一 contenteditable 里由浏览器原生排版完成；Rust 侧是 Dioxus 重渲染块列表后由桥 `focus_req` 恢复光标。两边都无动画——这是对的，给块插入加高度动画会和 contenteditable 光标打架，**不建议加**。
- **光标可见性**：Rust 的 `__mnFocus`（editor.rs 桥内）只做 `el.focus()` + 设 range，依赖浏览器 focus 的原生滚动。在本应用的 Safari 标签页几何环境（env 恒 0、视口高度动态）下，块在视口底部附近时原生 focus 滚动的落点不稳定，可能出现「光标已落位但被底部 chrome/工具条遮住一帧」的闪烁。原版单宿主不存在此问题（光标天然在文档流里）。这是 Rust 架构自带、与回车语义无关的衔接缺口，**建议单独补**：`__mnFocus` 设完 range 后在 rAF 里取光标 rect，仅当其超出可视区时 `scrollIntoView({ block: 'nearest' })` 做最小滚动——与斜杠面板 S3 的光标 rect 锚点是同一套工具，可复用。
- **连续回车**：原版口径下连按回车 = 空段不断累积（每次光标跟到新空段下方），与主流在普通段落上的行为相同，不构成问题；但叠加到待办上就变成「空待办 + 一串空段」。调优待办后（空待办回车退出为段落），连续回车自动收敛为普通空段累积，干净终止。

### 1.4 结论：局部调优（标题/标注保持，待办/引用改延续口径）

| 块类型 | 结论 | 内容 |
|---|---|---|
| 待办 todo | **调优（强烈建议）** | 有内容回车 → 按光标拆为两条待办（后段成新待办、未勾选）；末尾回车即新空待办。空待办回车 → 自身转为段落（退出清单，与 Rust 既有「空列表项回车退出列表」完全同构） |
| 引用 quote | **调优（建议）** | 回车按光标拆分、后段仍为引用（延续）；空引用回车 → 自身转段落退出。引用与列表同为「成组连续书写」的块，延续是普遍预期 |
| 标题 heading | **保持原版** | 末尾回车插空段与 Notion 逐字一致，是高频正道；中间不拆发生率低，且「标题不可劈」是可辩护的设计意图。仅补 1.3 的光标可见性平滑。若日后真机使用证明中间回车拆分呼声高，改动面极小（把 heading 移入延续组、新块带同 level），已在实现要点中预留 |
| 标注 callout | **保持原版** | 冻结格式里标注本就是 md 源段落（`> [!NOTE]`），编辑态回车是源码内换行，由 md 编辑通道管辖，不适用本议题的块级语义 |

调优不碰数据格式：拆分产生的仍是同类型 block JSON，与原版自身在其他路径（如粘贴、导入）产生的文档形状无区别；原版打开调优后产生的文档也能正常渲染（原版渲染层不依赖「待办后必跟段落」之类的假设）。

### 1.5 实现要点（落到 Rust 现有结构）

- 改动点单一：`op_split` 的 styled 分支（editor.rs:3084 一带）。现分支把 heading/quote/callout/todo 一并处理；调优后拆成三组：
  - `todo`/`quote`：移出本分支，走下方既有通用拆分路径——该路径已具备拆分 + 源块 DOM 回写（D1 修复）+ `focus_req` 落新块，只需让 `new_ty` 映射返回同类型（todo → 新 todo 且 `checked=false`，现代码已预置；quote → quote），并在进入通用路径前拦截「空块回车」子情形：before/after 皆空 → 自身 `node_type` 改 paragraph + 清类型字段（即恢复对齐前曾有的 split-exit-style 逻辑，但只对 todo/quote 启用）。
  - `heading`：留在现分支（插空段），一字不改。
  - `callout`：现分支里的 callout 实际走不到（标注是段落类型 + md 源），保留作防御即可。
- 列表项内的待办不存在（待办是顶层块），`Loc::Item` 不受影响；`Loc::Top` 守卫沿用。
- 光标平滑：桥 `__mnFocus` 的 attempt 成功回调末尾加 rAF + 光标 rect 可见性检查（`block:'nearest'` 最小滚动），一处改动覆盖全部结构操作（拆/合/转换/撤销恢复）的落点衔接，不只回车。
- 诊断：沿用现有 EDIT 标签，新增 `split-todo-continue` / `split-exit-todo` 等日志行，与 `split-styled-insert-para` 并存，便于真机回溯哪条路径被触发。
- 回归：probe_wave1 已有 B1 标题断言（标题整段保留 + 其后空段），保持不变即验证标题口径未动；需新增待办两例（连写三条待办全程只用回车；空待办回车后文档里无空待办残留）与引用一例（中段拆分两段皆为引用）。
