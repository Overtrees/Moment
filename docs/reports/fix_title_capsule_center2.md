# 标题胶囊预览态居中二次根治

- 日期：2026-11-28
- 批次：0.9.64 候选（已成笔，留主线组版）
- 实报：用户 0.9.63 装机——标题胶囊预览态「依旧没居中」，附截图（短标题「使用指南」4 字 + meta「09:56 · 共 147 字」）。

## 一、定性证据链

### 1.1 截图像素量测（本机 PIL 实测，@3x，px/pt = 3）

| 对象 | 墨迹/边界（px） | 中心（px） | 对胶囊中心偏差 |
|---|---|---|---|
| 胶囊玻璃 | x∈[405, 773] | 589（屏幕中心 589.5） | ≈0 |
| 标题行内框（胶囊 − 左右内距 20pt） | x∈[465, 713] | 589 | — |
| 标题「使用指南」墨迹 | x∈[463, 623] | 543 | **−46px ≈ −15.3pt** |
| meta「09:56 · 共 147 字」墨迹 | x∈[465, 712] | 588.5 | ≈0 |

推论（几何唯一解）：
- 标题墨迹左缘 463 ≈ 行左缘 465（差 2px 为墨迹/进距口径差）；标题字形块的排版原点 = 行左缘。
- 标题进距宽 ≈166px（4 字 × 14pt + kern），偏差预测 (行宽 248 − 进距 166)/2 ≈ 41px ≈ 实测 46px（墨迹口径差内）——与「字形块以行左缘为原点排布」模型逐值吻合。
- meta 墨迹宽 247px ≈ 行宽 248px：胶囊宽由 meta 定（capsuleWidth = metaW + 41 ≈ 123pt ✓ 与玻璃实测 122.7pt 合），meta 填满行宽，故「看似居中」是填满而非居中放置。
- 两行左缘差 2px 近齐：两行同享行左缘起点，标题宽 ≥ meta 宽时行宽 ≈ 标题宽、左对齐与居中无差别（偏差 ≈0.5pt 不可见），独「短标题 × 宽 meta」格暴露——与主线案情假设一致（proven）。

### 1.2 源码三路径盘点（MomentApp.swift titleCapsule，行号以 cf87bd3 计）

预览态共三条渲染路径：

| 路径 | 构造 | 居中构造 | 判定 |
|---|---|---|---|
| 截断覆盖层（>10 标量、未聚焦） | SwiftUI Text + `.multilineTextAlignment(.center)` + `.frame(maxWidth: .infinity)`（13113–13142） | 满宽帧 + 字形居中指令自带 | 初版已修、本批不动 |
| **非截断预览（≤10 标量、未聚焦）＝本案** | UITextField 本体可见（`.opacity(truncated ? 0 : 1)`，13077–13110） | 仅字段内部 `textAlignment = .center`（TitleTextField.swift:168）；行内放置无任何显式构造 | **坏层（proven）** |
| 编辑态（聚焦） | 同字段 | 同上 + 胶囊宽由全文量测驱动 | 本批帧对其同构生效（见 §三） |

容器层逐项排除（源码直读 + 像素互证）：页眉 HStack 双 Spacer 对称、胶囊帧居中（§1.1）；VStack(spacing: 3) 缺省 .center 对齐——meta 行（纯 Text、无宽度主张）被其正确居中（像素实测偏差 ≈0），证明容器对齐本身工作；`.glassControl` 为纯背景/裁剪修饰（GlassCard 源码），无布局作用；字段全仓仅一处构造，无第二呈现者。

### 1.3 坏层机制（proven 的部分与 inferred 的部分）

- **proven**：字段的字形块排版框 = 内容宽的盒、左缘与行左缘重合。由 UIKit 平台契约反推：`textAlignment = .center` 在字段帧宽 > 文本宽时必居中（无已知例外形态适用于短文本非编辑态），故截图形态 ⟺ 字段有效帧宽 = 内容宽且坐行左缘。即：representable 的 `sizeThatFits` 尺寸契约（TitleTextField.swift:234–251，「宽随提议」）只决定字段**自身协商宽**，在 shown 态的实际协商结果是内容宽——契约意图（回告提议宽 ⇒ 帧 = 行宽）未在该层级成立。
- **inferred**：协商在哪一拍落到内容宽（理想尺寸量测拍 vs 放置拍的提议形态），本机/tree 均无 SwiftUI 运行时可复现，不凭猜测写死；根治落点因此选在与协商结果脱钩的显式帧上（§三），不依赖该微观步成立与否。
- 历史旁证：B-4 换代前的 SwiftUI TextField 是原生灵活宽视图、自带占满行宽，同一容器结构下无此问题；问题随 representable 换代引入、随其后历次量测（竖排异常只盯纵向）未被横向复核。

## 二、上版为何漏

初版（fix_title_capsule_center.md）的定性表把字段形态判为「不偏（proven）」，依据是源码直读 `textAlignment = .center` + 前提 P2「两呈现者帧宽恒 = 行宽」。两处失守：

1. **前提按意图断言**：P2 的字段半句来自 sizeThatFits 契约的注释意图（「宽随提议」），从未在真机或宿主上量过字段的实际帧宽——断言锁的是声明，不是机制（与 0.9.57 三回归、Dynamic Type 声明锁同型）。
2. **量测矩阵自证**：T24-9 的纯核心 `centerDeviation` 把「块居中放置」写死为模型前提，矩阵中的「meta 更宽短标题（字段形态）」格（42/180）在模型内恒 0——该格测的是前提本身，不是呈现。矩阵缺的不是数值格，是**字段路径的结构锁**：覆盖层有 T24-8 锁其字形指令，字段路径没有任何断言锁「帧宽/放置」这一层。

本批补法按此教训分工：算式面归 T24-9（补本案数值格），结构面新增 T24-10 锁字段显式帧（见 §四）。

## 三、落码点（单点，提交 748b263）

**MomentApp.swift · titleCapsule 字段修饰链**：字段在 `.accessibilityHidden(truncated)` 后加显式 `.frame(maxWidth: .infinity)` + 根因注记。要点：

- 帧布局占满行宽并居中其内容：字段协商宽落在哪一档（内容宽或行宽），字形块中心恒合行中心——居中与协商宽脱钩，这是与上版「修指令」不同的「修构造」。
- ZStack 宽不变（改前改后恒 = 行宽：改前由字段协商/覆盖层帧决定，改后字段帧同为行宽），胶囊定宽、VStack 放置、meta 行几何逐值不变。
- 覆盖层是同 ZStack 兄弟视图，其 `.frame(maxWidth: .infinity)` 与 SpatialTapGesture 坐标系（原点在标题行左缘 = 覆盖层自身 bounds）逐字未动——落点映射守恒（§五复跑实证）。
- 编辑态同构生效：聚焦后字段仍在此帧内，短标题编辑时字形居中（与 0.9.35 定案「编辑/显示等距居中」同向）；长标题钳宽时提议宽确定、字段回告提议宽，帧为等宽无-op，溢出滚动等 UIKit 既有行为不变。
- 命中面：帧视图不自带命中，命中仍归字段本体帧（居中后的内容宽盒，与字形同位）——与改前「内容宽盒坐左缘」相比，命中盒随字形移到居中位，点按标题落焦行为等价且更合视觉。

**TitleTapCaret.swift · TitleCapsuleLayout 前提注释改判**：P2 改写为「行内占满与居中放置」（覆盖层自占行宽；字段靠显式帧；契约只管协商宽、不单独构成居中保证，初版按意图断言的沿革入注）；P3 尾「唯一层位」表述同步订正。纯核心算式（capsuleWidth / centerDeviation）逐字未动。

**覆盖层沿革注释订正**（MomentApp.swift 覆盖层注记）：「偏心唯一层位」改判为两呈现者各须自带显式居中构造，指向本报告。
