## 1. Web xsel 行为面全集（规格真源）

Web 的出发点：原版是单个 contentEditable 宿主、浏览器原生选区可跨任意块；Rust Web 版每块一个 CE 宿主、原生选区被钳在宿主内，故桥内维护**虚拟选区 xsel** 补齐（JS:375-387 注释自述）。其形态本身就是「多宿主 + 桥接层」的先例——这一点对路线选型是决定性的（见 §4）。

### 1.1 选区模型与呈现

| 项 | 规格 | 出处 |
|---|---|---|
| 模型 | `{a:{bid,off}, f:{bid,off}, fromStart, toEnd}`，端点 = 块 id + UTF-16 偏移（与 caretInfo 同口径） | JS:387 |
| 呈现 | CSS Custom Highlight `mn-xsel`，rgba(0,105,217,0.30)，逐块分段绘制 | JS:381-386、470-510 |
| 原子块呈现 | 端点块之间的非可编辑顶层单元（原子块/预览块）整块着色 | JS:490-509 |
| 双选区防重 | xsel 激活时原生选区收拢到锚点（placeNativeAt），避免两套选区同显 | JS:447-458、533 |

### 1.2 建立与扩展路径

| 路径 | 行为 | 出处 |
|---|---|---|
| 鼠标拖拽 | 单次按下（detail=1）接管：pointerdown 定锚、move 以 caretRangeFromPoint 逐点换算端点、up 收尾；指针压在原子块/块间隙时就近钳到相邻可编辑块边界 | JS:708-760 |
| Shift+点按 | 以现锚（xsel 或原生选区锚）扩展到点按处 | JS:713-723 |
| Shift+方向键 | 仅在跨块步进或已有 xsel 时接管，块内扩展放行原生；左右 = 字符步进（代理对不劈）；上下 = 光标矩形几何换算（边缘判定 + pointFromXY） | JS:622-686 |
| Ctrl/Cmd+A | 全文选区（首个可编辑块首 → 末块尾），置 fromStart/toEnd 标记；源码态块内不触发 | JS:582-587、858-905 |
| 双击/三击 | 放行原生（选词/选段是块内行为），同时清 xsel | JS:724 |
| **触摸** | **不接管**——长按原生块内选区保持现状（Web 在触摸端同样没有跨块选区） | JS:690-692 注释 |

> 关键事实：**Web 规格本身在触摸端就没有跨块选区**。跨块选区在 Web 上是鼠标/键盘（桌面）行为面。原生若只对齐 Web 已有行为面，触摸拖拽选区不在规格内——这大幅改变路线 (b) 的成本结构（见 §5）。

### 1.3 守卫集

| 守卫 | 规格 | 出处 |
|---|---|---|
| 源码态块禁区 | mdsrc / codeBlock / musicInput 不作端点、不可被跨越：焦点端钳到源码块近侧边界（guardSpan） | JS:388、512-534 |
| 组字 | keydown 组字守卫最先（composing/isComposing/keyCode 229）；compositionstart 先收拢 xsel；组字中 pointerdown 不接管 | JS:768、763、710 |
| 失效对账 | selectionchange：原生选区一旦不在锚点收拢（或展开为原生选区）→ xsel 作废，防陈旧跨度被下一次击键误替换；桥自身落点恒在锚点不误清 | JS:764-772 |
| 修饰键 | Ctrl/Cmd 按下（非 A/C/X）清 xsel；纯修饰键（Shift 等）不动选区 | JS:866-868 |
| 方向键收拢 | 无修饰方向键 = 收拢到有序起/止端（左/上→起点，右/下→止点） | JS:872-879 |

### 1.4 动作面（xsel 激活时）

| 动作 | 行为 | 出处 |
|---|---|---|
| 复制 Ctrl/Cmd+C | xselText()：逐块切片、块间以 `\n\n` 连接，写剪贴板 | JS:537-571 |
| 剪切 Ctrl/Cmd+X | 复制 + replaceRange('') | JS:865 |
| 删除 Backspace/Delete | replaceRange('') | JS:869 |
| 回车 Enter | replaceRange('', enter=true)：头尾成两块，光标落尾块首 | JS:870 |
| 打字覆打 | 任意单字符键 → replaceRange(char) | JS:881 |
| 粘贴 | xsel 在位时粘贴 = 整段替换（纯文本，多行在模型侧成块）；无文本则清 xsel 走常规分流 | JS:1714-1719 |
| Esc | 收拢到焦点端 | JS:871 |

### 1.5 模型 op：op_replace_range 语义（ops:617-…）

- 先行全量 sync（与 moveBlock/撤销同口径），保证模型与活 DOM 一致再手术。
- 端点排序后：起始单元取选区外侧 head 行内、止端单元取 tail 行内，中间文本块整块删除；插入文本按 `\n` 拆成结果块列，首行并入 head；光标落插入末尾（回车时落尾块首）。
- 结果块型随起始单元：顶层段落 → 段落列；列表项 → 列表项列，写回原列表，start 号按 E-17 口径递增修正（shift_list_start）。
- **K5 原子存活**：选区内（及全选时首尾外侧）的原子块全程存活、原位保留，替换按原子边界分段：首段承接 head+插入文本，尾行内由末段新块承接；无原子介入时与旧行为逐字不变。
- 全选清空且尾为空时不立空块，只留首段一个空段承载光标。
- 落盘/撤销：经文档变更正路（进撤销栈）；Diag 有 `EDIT replace range … ins=… enter=… atoms kept=…` 行。

## 2. 原生现状与差距全集

### 2.1 现状（proven）

- 每块一个 UITextView：BlockTextView（UIViewRepresentable，MA:2674）逐块（列表项亦然，listParent 形态）创建 EditorTextView（MA:2605）；全量 VStack 构建、无窗口化（F-19②）。
- 选区状态只存在于各 UITextView 自身的 selectedRange；EditorModel 只管焦点面：focusBlockId / pendingCaretOffset / focusCaretEnd + tvRegistry 弱注册表（MA:6462-6477）供落焦直达。**无任何跨块选区模型**（全仓无 xsel 等价物）。
- 复制/剪切：UITextView 系统原生，仅块内有效；EditorTextView 只覆写了 paste（成卡分流，MA:2620-2636），无 copy/cut 接管。
- 已有的跨块键盘面：跨块方向键 crossBlockArrow（MA:6437，audit2 E1 已修，硬件键盘、收拢光标语义）；pressesBegan → EditorModel.handleKey 分发链在位（MA:2639-2658），Shift 按压态有 shiftHeld 跟踪——**键盘接管的基础设施已经存在**。
- 模型 op 原语在位：splitBlock（MA:6165）、mergeBlockBackward（MA:6231）、deleteBlock（MA:6151）、pushHistory（MA:5972，上限 50，E2 批将改）。但无 replaceRange 等价物：跨块删除/替换的「head+tail 拼接、中间整块删、原子存活分段、列表 start 修正」语义在 Swift 模型层零实现。
- 组字守卫：markedTextRange 总闸在 shouldChangeTextIn（MA:2897-2899）、方向键组字不消费、组字期禁反写——守卫点分散三处（F-01 另有一处缺守卫，E1 批正收敛为单一判定源）。

### 2.2 差距全集（对 §1 逐项）

| Web 面 | 原生差距 |
|---|---|
| 选区模型/呈现 | 全缺：无模型、无跨块高亮 |
| 鼠标拖拽建立 | iOS 无鼠标常态（指针支持存在但非主面）；不列主差距 |
| Shift+点按扩展 | 缺（触摸点按无 Shift 语义）；不列主差距 |
| Shift+方向键扩展 | **缺**：硬件键盘下 Shift+方向只在块内扩展，到块界即止——与 Web 分叉的真实可达面（iPad+键盘） |
| Cmd+A 全选 | **缺**：现为块内全选（UITextView 原生 selectAll 仅本块） |
| 源码块禁区守卫 | 随选区模型缺失而缺 |
| 组字收拢/失效对账 | 随选区模型缺失而缺 |
| 复制/剪切跨块 | **缺**：跨块文本无法一次复制 |
| 删除/覆打/回车/粘贴替换 | **缺**：模型 op 本身不存在 |
| 触摸跨块选区 | Web 亦无——**不构成差距**（§1.2） |

即：真实差距集中在**键盘面（Shift+方向、Cmd+A）+ 动作面（复制/剪切/删除/替换/粘贴）+ 模型 op**；触摸面与 Web 等价（同为无）。

## 3. 路线 (a)：单 UITextView 多块化

把整个编辑器改为一个 UITextView 承载全篇（块以段落样式/附件区分），系统选区天然跨块。

### 3.1 冲击面逐项

| 既有机制 | 冲击 |
|---|---|
| 块呈现体系 | **根本冲突**：现行每块是独立 SwiftUI 行——卡片块（image/gallery/图文/音乐卡）、原子块、块菜单、拾起玻璃框、行级背景与让位动画全挂在「一块一视图」上。单视图内块只能是 NSTextAttachment/段落，卡片块的交互（点按开图片页、卡菜单、PHPicker 换图）要在 TextKit 附件里重造，等于另写一个编辑器。 |
| B-4 标题落点 | 标题是独立 TitleTextField，不受直接冲击；但正文落点链（focusBlockId/pendingCaretOffset → tvRegistry 直达）整体作废重写。 |
| 组字守卫 | 组字发生在单视图内、跨段 marked 语义与现行「组字期冻结本块模型」口径全变；F-01/E1 的守卫收敛成果大半作废。 |
| 拖拽仲裁 | DragPressEngine 的整套仲裁（长按拾起 vs 选区 vs 滚动）以「行」为单位，单视图下拾起对象变成文本范围——三轮战才收官的仲裁推倒重来，且与系统文本选区长按正面同体冲突（这正是 0.9.49 关掉 textDragInteraction 才解开的结）。 |
| 性能护栏 F-19② | 反向恶化：单视图全量 TextKit 布局，千块级文档首帧与每次编辑的全量重排比现行「每块一视图」更不可控；现行 sizeThatFits 签名缓存/强制全量布局的量测体系（MA:2744-）整体作废。 |
| 斜杠/浮层锚 | 斜杠面板锚、块菜单锚现按块 frame 回报（MA:6422、8546），全改光标 rect 口径。 |
| 双栏 | 两栏各一个编辑器实例的现行结构（independent/flow）要重做栏内单视图 + 跨栏禁区。 |
| MD 预览/未知块 | 失焦预览切换（paragraph+预览态）以块为单位，单视图内要做段级双态渲染，又一层重造。 |

### 3.2 量级与判读

- 改动面：MomentApp.swift 编辑器全域 + MomentDrag.swift + 呈现层，**8,000 行以上改动面、数千行新写**，且每一处既有定案（拾起规格、落点、量测、转场）都要重新真机终判。
- 行为等价度：理论最高（系统原生选区），但落地风险与回归面不可控，且与「行为等价即可、不掀根基」的既有工程口径正面相悖。
- **判读：不推荐。** 它解决的问题是「选区」，付出的代价是重写编辑器并作废三轮拖拽战与多批定案——根治的对象错位。

## 4. 路线 (b)：选区桥接层（Web 同构路线）

在多 UITextView 之上维护模型级选区，与 Web xsel 逐项同构——Web 已经证明这条路在「多宿主」架构下可行且行为面完整，原生是把同一设计移植到 UIKit：

### 4.1 组成

1. **选区模型**（新文件 MomentXSel.swift，按独立文件规矩不塞上帝文件）：`XSel { anchor:(bid,off), focus:(bid,off), fromStart, toEnd }`，由 EditorModel 持有；端点换算走既有 UTF-16 口径（与 pendingCaretOffset 同源）。
2. **高亮呈现**：逐块分段着色——端点间块在各自 UITextView 内以 attributed 背景色（同 Web rgba(0,105,217,0.30)）标出选段，中间文本块整块标，原子块行整体着色（行背景）。无新视图层级、不增视图数（对 F-19② 中性）。着色须与 didChange 的 runs 全量重算合拍：选区在位时重算后按选区重涂——这是呈现侧主要接线点。
3. **键盘接管**（硬件键盘面）：复用既有 pressesBegan → handleKey 链与 shiftHeld 跟踪：
   - Shift+方向：块内扩展放行原生（与 Web 同口径：仅跨块步进接管）——判据 = 原生选区焦点端已抵块界且方向向外；步进算法按 Web stepChar/几何换算移植（上下行走既有 crossBlockArrow 的目标列会话基础设施）。
   - Cmd+A：全选 + fromStart/toEnd。
   - 动作键接管：xsel 在位时 Copy/Cut/Backspace/Delete/Enter/打字/Paste/Esc/方向收拢逐项按 §1.4；Copy/Cut 需在 EditorTextView 覆写 copy/cut 或以菜单动作拦截（现 paste 覆写模式可循）。
4. **模型 op replaceRange**（Swift 模型层新写）：按 ops 语义逐项移植——head/tail 行内切分（split_inlines_at 等价物走既有 runs 操作）、中间整块删、插入按行成列、结果块型随起始单元、列表 start 修正、**K5 原子存活分段**、全选清空尾空不立块、光标回落（focusBlockId/pendingCaret 既有链）、pushHistory 进栈、Diag `EDIT replace range` 同式打点。E3 批的 clearTypeFields 单点化落定后，结果块的字段清理口径与其对齐（不在本 op 内另写一份）。
5. **守卫集**：源码块禁区（codeBlock/mdsrc/musicInput 端点钳制，guardSpan 移植）；组字收拢（marked 开始 → 收拢到焦点端，挂 E1 收敛后的组字判定单点，**不另起守卫**）；失效对账（各视图 textViewDidChangeSelection / 落焦变更时核对原生选区是否仍收拢于锚点，否则作废——selectionchange 的 UIKit 等价物）；程序化落点（__mnFocus 等价路径）使选区失效。

### 4.2 触摸面的取舍（本路线的关键裁量）

Web 触摸端不接管（§1.2），原生对齐即：**触摸长按选区仍为块内行为，跨块选区只经键盘面建立**。若要超出 Web 规格、在触摸端也做跨块拖拽选区，则必须自管全套触摸选区交互：iOS 的系统选区句柄属于单个 UITextView，长按拖动无法把句柄拖进另一个视图；自管意味着自研手势跟踪 + 自绘句柄/放大镜 + 与 DragPressEngine 争夺同一长按（拾起拖拽的仲裁刚收官）+ 系统编辑菜单时机自理。这是与 Web 规格无关的新增产品面，成本与风险独立成量级（见 §6 表 (b2)），且终判全压真机手感。**本评估将其拆为独立子期 (b2)，不与 (b) 主体捆绑。**

### 4.3 量级

- 新码：MomentXSel.swift 约 700–1,000 行（模型+呈现+键盘接管）+ replaceRange 模型 op 约 300–450 行 + 接线改动约 400–600 行（BlockTextView 着色钩、handleKey 分发、EditorTextView copy/cut、失效对账点）。合计 **约 1,400–2,000 行**。
- 行为等价度：键盘面与 Web 逐项等价；触摸面与 Web 等价（同为无跨块）；呈现色值同源。

## 5. 路线 (c)：降级子集

| 子集 | 内容 | 覆盖面 | 量级 |
|---|---|---|---|
| (c1) 全选动作面 | 仅 Cmd+A 建立「全文选区」这一特例（端点恒为首尾，无任意端点跟踪）+ 高亮（整块着色，无段内分段）+ replaceRange op + 复制/删除/替换/粘贴动作 | 覆盖 §1 动作面中以全选为入口的全部 + 整篇复制；**不覆盖**任意跨块区段的选择/复制/删除 | 约 500–700 行（其中 replaceRange op 约 300–450 行与 (b) 共用，是 (b) 的真子集） |
| (c2) 块级多选 | 以整块为粒度的多选模式（勾选块 → 批量复制/删除/移动），粒度是块不是文本 | 覆盖「整段搬运/整批删除」意图；不覆盖文本级区段操作；且 Web 无此面——是原生自创产品面，需另定交互（与拾起/卡菜单的关系要设计），并非纯降级 | 约 600–900 行 + 交互设计成本 |
| (c3) 仅跨块复制 | 只做选区建立 + 复制，不做删除/替换 | 仍需 (b) 的选区模型+呈现+建立路径全套，只省一个模型 op——成本约 (b) 的 75%，收益只有一项，**性价比最差，不推荐单列** | 约 1,100–1,500 行 |

注：(c1) 不是独立路线，而是 (b) 的第一期切分——op 与模型先行，任意端点跟踪随后补齐即可达 (b) 全量，无返工。

## 8. 推荐与登记口径

### 8.1 推荐：路线 (b)，分两期；(b2) 缓做

- **一期 = (c1) ∪ (b) 的模型/op/键盘骨架**：replaceRange 模型 op（含 K5 原子存活、列表 start、Diag）+ Cmd+A 全选 + 全选态高亮 + 动作面（复制/剪切/删除/回车/覆打/粘贴替换）+ 组字收拢与失效对账守卫。约 500–700 行起步即覆盖整篇处理与整篇复制——这是跨块选区在触屏设备上最可能被真正用到的部分（配合外接键盘/大屏），且全程不碰触摸仲裁。
- **二期 = 任意端点键盘扩展**：Shift+方向跨块步进（含上下几何换算）+ 段内分段高亮，补齐与 Web 键盘面的逐项等价。约增 700–1,100 行。
- **(b2) 触摸跨块拖拽选区：缓做并登记**。理由：Web 规格本身无此面（不做不构成 parity 缺口）；iOS 系统句柄不可跨视图，自管交互与拾起长按仲裁正面相争、终判全压真机手感，成本/风险与收益（unknown，无使用数据）不相称。待一二期落地后若真机使用中确有触摸跨块诉求，再以独立评估立项。
- 否决 (a)：掀编辑器根基、作废拖拽三轮战与多批定案、与 F-19② 护栏反向（§3）。
- 否决 (c2)：Web 无此面，是自创产品面而非降级，且粒度（整块）不解决文本区段诉求；块级批量删除的真实诉求可由现行逐块删除+撤销覆盖大半。
- 否决 (c3)：成本约为 (b) 的 75% 只换复制一项。
