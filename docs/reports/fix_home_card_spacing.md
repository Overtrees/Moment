## 用户实报与量测

用户截图（2026-11-27 16:58）：「今天」组内图文卡与下方文本卡之间的空白明显大于其余卡间节奏（红箭头）。对原图做像素量测（@3x，取 x≈89% 列——避开文字与圆角弧段、圆角偏置 <1pt）：图文卡白边下沿 y=1298px、文本卡白边上沿 y=1519px，**背景段 = 216px = 72.0pt**。账面应为 40（见下）。同图交叉校准：文本卡→次组组头合成、组头→图卡距、卡内白条高度三处与源码账的偏差均在字形量测噪声内（±3pt 级），唯独图/文交界偏差 +32（约噪声的 10 倍）——异常被隔离在交界这一处。

## 定因（proven：消去法 + 交叉校准）

窄屏 List 内每一行的行间距都由该行显式声明的 `listRowInsets` 决定（9 行构造：占位/横幅/notice/新建卡/组头/备忘行 ×2 子列/分隔行/底部留白/空状态）。逐行核对源码：

- 图文卡、文本卡均为同一 `memoRow` 构造，insets 恒 (3,16,3,16)——卡型对维度上**不存在分叉的行构造**（音乐/链接/附件类备忘与文本卡同行同 inset；仅封面派生命中者进图子列，天气只存在于新建卡内）。
- 两子列之间的唯一行 = C-A3 分隔行 `Color.clear.frame(height: 34)`（0.9.36 批 C 落码，1e24756）。**它是全 List 唯一未声明 `listRowInsets` 的内容行**（空状态行同病，见同族排查）——未声明即静默继承系统默认 insets。账面合成 3+34+3 = 40 是按「零默认 insets」写的（注释里就这么算的），实测 72，残差 32 只能来自该行的默认纵向 insets（合计 32、单侧 16/16 为 inferred）。
- 消去其余候选：分隔行重复插入会给出 74（单份 insets）或 138（双份），与 72 不符；List 最小行高假说给出 50，不符；glassCard 修饰器无外部 padding（源码核毕，且若有则全卡型同受、与交叉校准矛盾）。唯「单行 + 默认 insets 继承」与实测精确吻合。
- Web 真值（proven，源码）：图/文交界 = img 子列 `.list-group` margin-bottom 24（base.css:111）+ `.gap-16` 高 16（base.css:205、main.rs:2505 插于两子列之间）= **40**；卡间 = `.swipe-wrapper`/`.img-card` margin-bottom 6（base.css:118/191）。原生账面 40/6 本与 Web 一致，坏在账面赖以成立的修饰器根本不存在。

## 根治（单一规则，非逐对补丁）

规则收敛为一句话：**ListView 内每一行必须显式声明 `listRowInsets`、零默认依赖**——该规则本就是全 List 的既成事实（9 行中 7 行早已显式声明，含同族的占位行与底部留白行同为 `Color.clear` 行且都带 `EdgeInsets()`），本批只把两处违例行带回规则内，交界间距的异常随之消失，不对任何卡型对单独设值：

| 落点 | 改动 |
|---|---|
| C-A3 分隔行 | 补 `.listRowInsets(EdgeInsets())`（与底部留白行同序同形）；注释补记本教训（账面按零默认 insets 计算而修饰器缺席） |
| `emptyRow` | 补 `.listRowInsets(EdgeInsets())`；纵 56 的账面值（线 B B-4）自此真实成立 |

未抽共用构造函数的理由：三行 `Color.clear` 中占位行另挂滚动探针的 onGeometryChange 机器，形态各异；三者共享的不变量就是 insets 声明本身，故以计数锁守不变量（下条），而非为抽而抽。

## 附图另两处定性

1. **封面区高度/比例——合 Web 规格，非缺陷**（proven）：Web `.img-cover` aspect-ratio 16/9（base.css:193），原生同以卡宽 × 9/16 定高；截图量测封面高 ≈201–203pt，计算值 = 卡宽 361 × 9/16 = 203.1pt，吻合。「观感偏高」是全宽卡 16:9 的规格本身，不动。
2. **封面未加载占位——与 Web 不符的呈现差，列调优候选、本批不落码**：Web 无图态 = `.img-cover` 空灰面（background var(--border-color)、无图标；list.rs:1148/1212 的 div 形与 alt="" 的失败 img 在 WKWebView 下均不渲染图标）。原生 `ItemImageView` = 灰面（secondary 15%）+ 居中 SF 图标（加载中 `photo`、失败 `photo.badge.exclamationmark`）。图标承载加载/失败状态反馈，按「增强可保留」口径可留；若用户裁严格对齐 Web，去图标仅留灰面即可（同时失去加载/失败区分，属观感裁量级）。另注：截图两卡同为失败态，根源是其封面附件在该设备缺失（数据面；Web 同场景亦只剩灰面，list.rs:1107），非布局问题。
